# 04 · UI 改動

UI 目標(對應題述需求):

1. **user 看得到壓縮發生了**(聊天列中的 cmp entry)。
2. **user 看得到「實際送出的資料」**(inspector,WYSIWYG)。
3. **進階 user 可人工介入**(編輯 summary、移動斷點、手動壓縮/還原)。

## 1. 聊天列:compaction entry 渲染

### 1.1 分派

`ChatMessage.svelte:407` 的分派鏈新增一個 branch(與 `isSynthetic` 同位級):

```svelte
{#if message.role === MessageRole.SYSTEM}
  <ChatMessageSystem ... />
{:else if message.type === MessageType.COMPACTION}
  <ChatMessageCompaction class={className} {message} />
{:else if mcpPromptExtra}
  ...
```

`ChatMessages.svelte` 的 `displayMessages`(`:136`)grouping 迴圈:
cmp 是獨立 display entry(不被 assistant 的 tool-grouping 吃掉;
迴圈裡 `role === TOOL` 會 skip,cmp 是 `user` role 所以本來就不會 skip,
只需確認 agentic grouping 的 `while` 不會把後續訊息併進來 ——
cmp 之後通常接著 user 訊息,自然斷開;補一個測試覆蓋)。

### 1.2 `ChatMessageCompaction.svelte` 內容(收合式)

```
┌──────────────────────────────────────────────────────┐
│ ⟳ Context compacted · 2026-10-13 02:14               │
│   摘要了 3 則訊息(約 1,840 → 420 tokens)             │
│   [展開摘要]  [編輯] [重新摘要] [還原全部上下文]      │
└──────────────────────────────────────────────────────┘
  展開後:summary 全文(可捲動,mono 選單式排版)+
        「保留起點:第 4 則(user:『帮我修…』)」

  split 切(isSplitTurn)時:
  標題「Context compacted (mid-turn)」,
  保留起點顯示「第 7 則(assistant: tool_calls read_file)」,
  並標註「此 turn 的使用者請求已含於摘要」。
```

- 視覺上刻意**不像** user 氣泡(中央細條、muted 色、icon),
  避免被當成對話內容;與 `ChatMessageSynthetic`(cwd 行)同級別的存在感。
- 動作(都走 `chatStore` 新方法,見 05 計畫):
  - **展開摘要** — 純本地 state。
  - **編輯** — 就地 textarea(或開 inspector 的編輯區);存檔 =
    `updateMessage(cmpId, { content })`。
  - **重新摘要** — 對同一 summarize 區重跑 summary(模型可選)。
  - **還原全部上下文(expand)** — 確認對話框:顯示
    「上下文將從 ~420 增回 ~1,840 tokens」→ 刪 cmp 節點、子節點重掛、
    更新路徑。
- `settingsStore.config.contextShowCompactionEntries = false` 時
  整列不顯示(送出邏輯不受影響,inspector 仍可見 cmp)。

## 2. Context Inspector(核心新增元件)

### 2.1 定位

**「這一輪送給 LLM 的,精確就是這些」** — 進階/除錯視角。
資料來源 = `buildLlmContext(conversationsStore.activeMessages)`(與送出同源)。
非 streaming 時顯示「將送出」;streaming 中顯示「本輪已送出」的快照
(在送出前抓一份存起來即可,避免 chunk 期間重算)。

### 2.2 版面(桌面 Dialog,行動端 Drawer,與既有 dialog 慣例一致)

```
┌ Context Inspector ──────────────────────────────── [Copy JSON] [×]
│  模型: qwen3-32b   n_ctx: 32,768
│  真實 context: 153,939 tok (59%)  ▓▓▓▓▓░░░░░░░░░   (＝gauge contextUsed)
│  ─ 實際訊息列(= payload)────────────────────────
│  [system]  You are a helpful…            -     (2.1KB / ~525 est.)
│  [summary] (compacted 3 msgs)            420   (1.7KB / ~425 est.) ← 可點「編輯」
│  [user]   帮我修這個 bug…                310   (1.2KB / ~300 est.)
│  [asst]   (tool_calls: read_file)        120   (480B  / ~120 est.)
│  [tool]   ── file content ──             640   (2.6KB / ~640 est.)
│  …                                        …
│  ─ 已裁切(不送出)──────────────────────────────
│  [user]   早先的問候…            (被 summary 涵蓋)
│  [asst]   …
│  ─ 進階 ────────────────────────────────────────
│  保留起點: (user)「帮我修這個 bug…」 [選擇…]*
│  [Compact now]  [Expand(還原)]  [重新摘要]
└──────────────────────────────────────────────────────
```

- **每則一行**:role badge、content 單行截斷(點開看全文/attachments 佔位)。
  **主欄**＝真實 token(assistant=`predicted_n`、段真實總和、system=`-`、尚未送出尾端=`est.`);**副欄**＝`bytes` / `bytes÷4 est.`(參考,非主值)。總和條＝**真實 `contextUsed`** 對照 `n_ctx`(＝gauge,顏色級別複用 `context-gauge.ts` 的
  `colorLevelFromPercent`)。
- **「已裁切」區**:把 drop 的訊息以灰階列出,讓 user 明確知道
  「哪些沒送、為什麼」(被哪筆 cmp 涵蓋、或斷點失效警告)。
- **Copy JSON**:完整 `ApiChatMessageData[]`(base64 以佔位符
  `[image: 3.2KB base64]` 表示,避免 clipboard 爆掉;提供
  「含完整 base64」選項)。
- **斷點選擇器**:下拉列出 I4 合法斷點 —「role=user 或 assistant 的訊息」,
  分兩組:「回合邊界(user)」/「turn 內(assistant)」;不列 tool result。
  前移/後移的語義與確認文案照 02-data-model §4;
  選到 assistant 斷點即成為(新的)split 切,需重摘要時照常提示。
  **空 kept 狀態**(`firstKeptMessageId` 缺,全部壓縮):選擇器顯示
  「無保留訊息(全部壓縮)」;只能前移(選一則訊息 = 恢復 kept,只改
  metadata)、不能後移;Re-summarize 的 region = cmp 之前的所有訊息
  (排除 cmp 節點本身)。
- **boundaryValid = false**(id 存在但已不在路徑上)時,頂部紅色警告條:
  「斷點訊息已不存在,目前全量送出 — 建議重新壓縮」+ 按鈕。
- **停止按鈕（已實做，N3）**：`compacting` 期間（手動 Compact now /
  重新摘要/斷點後移的重摘要),動作列的觸發鍵變 [Stop]——中斷 summary
  呼叫(不建 cmp、toast「已停止」、fail-open)。in-loop 的停止沿用
  flow abort(不另加)。

## 3. Context gauge 的 compaction 指標

`contextStatsStore` / gauge popup 增一列(有 cmp 時):

```
Compacted: 3 entries · ~1.4k tokens saved   [Inspect →]
```

- `contextUsed` 本身不需要改:它來自**下一輪** server 回傳的
  `prompt_n`,compaction 後自然下降(這是「真實值」,不要手算覆蓋);**同時是 Context Inspector 標題/總和條的來源**(v4,見 §2)。
- **比例條分母 / 觸發標記跟 active mode 走(雙 mode)**:mode A =
  有效視窗 `min(n_ctx, contextMaxContextOverride)`、觸發點 =
  `window − keepRecentTokens`;mode B = `n_ctx`、觸發點 = `threshold% × n_ctx`。
- 「saved」數字 = `cmp.compactionMeta.estimatedTokensBefore -
  estimate(當前 payload 的真實 token 和,v4)`,純顯示用途。
- 自動壓縮進行中:`Compacting context…`(spinner),完成後 toast。

## 4. Settings(新 key)

加在 `SETTINGS_KEYS` + `SETTINGS_REGISTRY`(General 或新設
「Context」section;第一版放 General 即可,少一個側欄項目):

| key | 型別 | 預設 | 說明 |
| ---- | ---- | ---- | ---- |
| `contextAutoCompaction` | CHECKBOX | `false`(experimental) | 超過門檻自動壓縮(flow 之間) |
| `contextCompactionMode` | SELECT | `recent-window`(A) | **compaction mode**(雙 mode,2026-10-17):A = recent-window(pi reference,至少留最近 keepRecentTokens 原樣、觸發 = window−keep)/ B = threshold-target(v3,kept ≤ (threshold−keepTarget)%、成功判定 summary ≤ keepTarget%,v4:head 不計);`dependsOn: contextAutoCompaction` |
| `contextAutoCompactionInLoop` | CHECKBOX | `false`(experimental) | agentic 迴圈 turn 之間自動再壓縮,`dependsOn: contextAutoCompaction` |
| `contextMaxContextOverride` | INPUT(0 = 關) | `0` | (mode A)user 覆蓋 model n_ctx 為有效視窗:`min(n_ctx, override)`;只用於裁切決策,不硬限實際送出;`dependsOn: contextCompactionMode` (=A) |
| `contextKeepRecentTokens` | INPUT | `20000` | (mode A)要保留的最近窗口(下限目標;walk 以真實 token 加算、無資料例外 bytes/4;設定數字不變現為 token 尺度,見 02-§3.4);`dependsOn: contextCompactionMode` (=A) |
| `contextCompactionThreshold` | INPUT(1–100) | `70` | (mode B)自動壓縮**觸發點**(% of n_ctx,「ctx 到這個 % 才檢查」);`dependsOn: contextCompactionMode` (=B) |
| `contextKeepTargetPercent` | INPUT(10–90) | `50` | (mode B)**compact target**:summary 成功判定 ≤ 此 % of n_ctx(v4:head 不計);budget = threshold − 此值(06-status §3.14/§5c N2);`dependsOn: contextCompactionMode` (=B) |
| `contextSummaryMaxAttempts` | INPUT(0–10,0 = 無限) | `3` | (**共用**)summary 超標重試次數(總計;1 = 一次;≤ 0 = 無限)→ 仍超則 gate 三選項;`dependsOn: contextAutoCompaction` |
| `contextKeepMinUserTurns` | INPUT(1–50) | `4` | (**共用**)kept 區至少保留的最後 N 則 user 訊息(邊界切 / A 切點落 user 訊息時) |
| `contextKeepMinMessages` | INPUT(0–50) | `0` | (**共用**)kept 區至少保留的訊息數(split 切;預設 0 = 允許空 kept,N6) |
| `contextSummaryMaxTokensPercent` | INPUT(10–90) | `70` | (**共用**)summary 長度上限 = n_ctx × 此 %(跟模型走:128k → ~91k、256k → ~183k;取代舊固定 `contextSummaryMaxTokens`,見 06-status §3.13) |
| `contextShowCompactionEntries` | CHECKBOX | `true` | (**共用**)聊天列顯示 cmp entry |
| `contextSummaryMode` | SELECT | `prefix-stable` | (**共用**)summary 的 prompt 模式:prefix-stable(原結構逐則送、KV 前綴重用)/ transcript(v1 扁平文字);逃生門——server 拒絕 prefix-stable payload 時切回(見 06-status §3.19) |
| `contextSummaryPrompt` | TEXTAREA | 見 02-§5 | (**共用**)自訂 summary 指令(進階) |

> **dependsOn 鏈(雙 mode)**:`contextAutoCompaction` → `contextCompactionMode`
> → {A: `contextMaxContextOverride` / `contextKeepRecentTokens`} /
> {B: `contextCompactionThreshold` / `contextKeepTargetPercent`};其餘欄位直掛
> `contextAutoCompaction`。舊 threshold/keepTarget 的 dependsOn(auto)→ 改掛
> mode;settings-registry-invariants 測試需同步更新。

> 預設 `false` 的理由:compaction 會丟細節(以摘要換空間),
> 對本地 LLM 使用者是行為變更;inspector 與手動壓縮不受此開關影響,
> 想用的 user 可手動。

### 4.1 超標確認卡片(共用,兩 mode)

`ChatCompactionDecisionCard.svelte`(與 agentic continue 卡片同風格):

- 顯示:這次壓完的實際數 vs mode 目標(A: `summary + kept` vs
  `window − keepRecentTokens`;B: `summary` vs `keepTarget% × n_ctx`,v4:head 不計)+
  已重試次數。
- 三選項:[使用這次壓完] [重壓] [這次不壓];abort(flow stop / Stop)= skip。
- 掛法:in-loop = agentic 訊息內(與 continue 卡片同位);
  flow 之間 = 訊息列尾端獨立 row。

### 4.2 壓縮進行中指標列 + 輸入 queue(N7,設計定稿 2026-11-04;未實做)

> 背景:post-flow 自動壓縮兩個觸發點是 fire-and-forget(`void
> compactConversation`),I7 guard 只在開頭檢查一次、`sendMessage` 不查
> `compacting` —— summary 期間 user 立刻送下一句會造成樹競態(cmp 懸空 →
> Summary 靜默丟失;且該句以未壓縮全量 context 送出 → overflow 風險)。
> 手動 Compact / Re-summarize / 斷點後移同窗。in-loop 不受影響(loop
> block、輸入走 steering)。分析與時序見 06-status §3.26。
> 使用者決策(2026-11-04):**queue 不 block** + in-chat 明確指標列(含 Stop)。

**指標列 `ChatMessageCompacting.svelte`(新)** —— 訊息列尾端獨立 row(與超標
確認卡片同錨點),位於 pending/steering row **上方**:

    ┌──────────────────────────────────────────────────────┐
    │ ⟳ Compacting context…                                │ [Stop]
    └──────────────────────────────────────────────────────┘

- 顯示條件(三者皆須成立):
  1. `contextStatsStore.compacting && compactingConvId === activeConv?.id`
     (per conversation:conv A 背景壓縮不在 conv B 顯示/阻擋 —— in-loop 明確
     支援「user 切走後繼續跑」);
  2. `activeMessages` 尾端**不是** cmp 節點(完成瞬間真 cmp row 接手,避免雙列);
  3. 超標確認卡片未顯示於列表(post-flow gate 時卡片即可操作指標;in-loop
     卡片掛在 agentic 訊息內,此條件不成立、指標列照常顯示)。
- Stop 按鈕依情境分派:

  | 情境 | 判定 | 動作 |
  | ---- | ---- | ---- |
  | in-loop(agentic running) | `agenticStore.isRunning(convId)` | `chatStore.stopGeneration()` — flow signal 中斷 in-loop summary(fail-open、不建 cmp)→ flow 結束 |
  | post-flow / 手動 | 否 | `chatStore.stopCompaction()` — 中斷 summary 呼叫(fail-open、不建 cmp、toast「Compaction stopped」) |

- `role="status"` + `aria-live="polite"`;視覺與 `ChatMessageCompaction` 同級
  (中央細條、muted 色)。

**輸入 queue(queue 不 block)**:

- 輸入框**不 disable**;壓縮期間送出走 `chatStore.sendMessage` 的新 guard
  (第三層,在 steering / streaming-pending 之後):
  `compacting && compactingConvId === convId` → `injectPendingMessage`
  (既有 single-slot pending;後送覆蓋前送,與 streaming 期間同語義)→ return。
- queue 中的訊息由**既有** `ChatMessageUserPending` 顯示(指標列下方;
  支援 edit / delete / send-immediately —— 零改動)。
- **自動送**:chatStore 三條 compaction 路徑(`compactConversation` /
  `moveCompactionBoundary` 後移 / `recompactConversationEntry`)的 `finally`
  共用 finalizer(`compacting` 重置後):consume pending → 有則
  `sendMessage`(此時 guard 已過)。**任何**結束(成功 / gate skip / summary
  失敗 / abort)都跑 —— queue 的訊息不會被丟下。in-loop 路徑不 consume
  pending(該處輸入已在 guard 第 1 層走 steering;steering 由下一 loop
  iteration 消費,既有行為)。
- 壓縮期間 pending row 的「Send immediately」(ArrowUp):`abortCurrentFlow`
  補一個 `stopCompaction()`(無手動壓縮時為 no-op)→ summary 中斷 →
  finalizer 自動送 queue 的訊息。

**store 層 guard 是競態主修,UI 為第二層**:`compacting = true` 前移至 guard
檢查通過後立刻(在 path 解析 / plan 之前,收掉 async 窗口);
`compactingConvId` 與 `compacting` 原子設定/清除(`setCompacting(convId | null)`
helper)。四條路徑(chatStore 3 條 + agentic `compactBetweenTurns`)皆帶 convId。

## 5. 對話標題 / 搜尋 / 匯出 的相容性

- **標題**:cmp 不是 USER role 的「第一則 user 訊息」候選
  (`applyTitleFromContent` 找的是 role=user 且有內容的第一則;
  cmp 是 user role → 理論上可能當選?cmp 只會在對話中後段出現,
  第一則 user 訊息一定在 cmp 之前,安全;補測試)。
- **搜尋**(conversation 內容搜尋):summary 文字應可被搜到
  (它就在 `content` 欄位,免費)。
- **匯出**:JSONL 原樣帶出 `type:'compaction'` + `compactionMeta`;
  匯入側 `parseSessionsJsonl` 不需改(整則 object 進 DB),
  但 `toolCalls` 的 string 化邏輯對 cmp 無影響。補 round-trip 測試。

## 6. 可存性/可接近性(a11y)

- cmp entry:`role="status"` 或普通 block + 可聚焦的展開按鈕;
  收合狀態用 `aria-expanded`。
- Inspector:標準 Dialog(既有 shadcn dialog 元件),
  焦點陷阱、Esc 關閉、title/description 完整。
- 還原(expand)的確認對話框沿用 `DialogConfirmation` 模式。
